# テスト戦略

テストは、変更によって壊れる可能性がある振る舞いを最も低い層で検証する。同じ振る舞いを複数の層で繰り返さない。

## テストを選ぶ

| 変更対象                | 読む文書                                     |
| ----------------------- | -------------------------------------------- |
| フロントエンド          | [フロントエンドテスト](frontend/README.md)   |
| Drizzle、SQL、migration | [データベーステスト](../database-testing.md) |

新しいテスト種別を導入するときは、この表に責任範囲を追加し、既存のテストとの重複を解消する。

## 共通方針

- 公開された振る舞いを検証する。実装内部をテストへ固定しない
- mockより実際の実行環境を優先する
- 失敗時に原因を追えるartifactをCIへ残す
- flakyなテストをretryで常態化させない。入力、時刻、乱数、外部通信、実行環境を固定する
- bug修正では、修正前に失敗して修正後に成功するテストを追加する

## 完了条件

変更に対応するテストが最も低い適切な層にあり、ローカルの対象テストと`vp check`が成功すれば完了とする。複数の層を使った場合は、それぞれが異なる責任を検証していることを確認する。
